# Idle_Outpost AI 辅助测试实施框架

日期：2026-10-16。状态：**M0、M1基础协议及全自动文档分析首版均已由用户确认验收；M3设备自动化和AI自主规划仍按后续阶段推进**。

本轮已完成项目勘察和最新 v65 包体安装。以下描述确认后的实施顺序；每个阶段完成一次真实闭环再向后推进。

## 先选路径

推荐“确定性工具和证据先行，再加入 AI 规划”。仅靠视觉控制可以探索发布包，但无法可靠证明等级、金币等业务状态；Unity 测试桥能够提供状态和业务断言，需要独立的测试构建。两者共用运行记录与工具接口。

首个业务场景拟定为：**进入主界面 → 打开升级面板 → 执行一次指定设备升级 → 验证等级及资源变化 → 留下可回放证据**。

开始该场景前先落实测试服和隔离账号。由于设备标识登录，单独清除应用数据不足以重置业务进度。

路线实测时固定具体 `upgrade_id/type`、单次升级模式和 UI 入口。旧合同的 terrain upgrades 入口不能直接视为当前包的设备升级入口；旧 `Level_1_0`、device ID `1` 也需在实际测试基线核验。放置收益和奖励会并发改变货币，应隔离收益或取得本次升级事务记录，不能用未经解释的余额差额判定成本扣除。

## 阶段与验收

| 阶段 | 怎样实现 | 最小闭环与产物 | 验收出口 |
| --- | --- | --- | --- |
| M0：数据与版本基础 | 定义 requirement/case/run/evidence/defect 等 ID；本地 JSON/JSONL 配合索引，固定构建、源码、环境、模型/工具版本 | 人工录入一条验收契约→校验→关联用例和运行→导出追溯报告 | 缺少必填来源或环境时拒绝业务执行；未知构建来源明确为 unknown，不能填当前源码冒充 |
| M1：AI 辅助需求分析 | 从原DOCX自动提取正文/表格/删除线/内嵌表与图像；真实模型生成需求、风险、测试点和引用用例；支持Codex CLI与可配置独立API，由测试人员审核 | 原文档→自动模型调用→结构校验→问题/风险/测试点/用例草稿→人工审核→结果登记 | 一条命令从真实文档产出，无人工预填分析JSON；逐节/逐图可追溯，审核状态分离；失败不冒充AI成功，未绑定不执行。详见M1新增验收清单 |
| M2：Android 确定性冒烟 | 封装设备发现、包身份核验、更新安装、Activity 启动、定时观测、截图和进程日志；所有调用显式选择设备 | 指定包和设备→启动→验证进程及预定义稳定界面→输出报告→用同一参数复跑 | 测试环境先核验；报告有命令/退出码/时间/证据/结果；证据不足不能宣称业务通过 |
| M3：首次升级业务闭环 | 在专用测试构建加状态桥，读取 UGUI 窗口/元素、设备等级、货币、引导状态；确定性运行器执行安全操作及断言 | 固定账号和进度→采集升级前状态→操作一次→采集后状态→等级/资源断言→报告和回放 | 独立期望值来自审核契约/配置；观察状态来自游戏；禁止“点击成功即升级成功”；指定基线连续5次完成，注明样本有限 |
| M4：受限 TestAgent 与缺陷链路 | AI 根据目标和当前状态选择白名单工具，受步数/超时/成本约束；断言仍由确定性代码执行；失败复核、归类、去重 | 批准用例→观察/计划/执行循环→证据→结果→缺陷草稿→人工确认→复现/回归 | 与确定性路线用同一验收契约；安全重复时才重试，升级类操作不能盲重试；模型/工具失效不当游戏Bug |
| M5：评测与治理 | 建立20～30条黄金任务/回归场景；包含正常、已知失败、弹窗、加载延迟、工具失效；冻结评测配置 | 固定版本→执行黄金集→指标与基线比较→决定保留/回滚模型、Prompt或工具变更 | 正/负例均有独立标签；采样量和置信限制可见；未见真值的未知Bug不能用于计算漏报率 |
| M6：专项扩展 | 在相同结果契约上逐项接入弱网、设备矩阵、性能、稳定性、热更/强更/回滚和后端压测 | 选一项专项→固定参数→工具执行→监控关联→报告→恢复环境 | 每项具备可重复实验、性能/稳定性基线和恢复办法；压测只指向授权测试环境 |

M0/M1 的执行记录允许人工产生，不能冒称 Agent 自动执行。M2 可以先形成工程闭环；M3 是第一条带可靠游戏状态断言的业务闭环。

## 拟定模块与责任

实施时根据确认后的接口细化文件，以下为拟定目录，不代表已存在：

| 拟定目录 | 责任 |
| --- | --- |
| `src/ai_test_agent/contracts/` | 需求、用例、运行结果、证据和版本字段校验 |
| `src/ai_test_agent/ingestion/` | 文档、配置、接口、变更和历史缺陷的授权采集及来源定位 |
| `src/ai_test_agent/adapters/android/` | ADB/bundletool调用、设备目标、安装、观测和日志采集 |
| `src/ai_test_agent/adapters/unity/` | 状态桥客户端与Unity坐标/业务状态映射 |
| `integrations/unity-test-bridge/` | 本仓库维护的专用测试桥源码与接入说明，不复制完整游戏源码 |
| `src/ai_test_agent/runner/` | 确定性步骤、等待、断言、超时、运行追溯 |
| `src/ai_test_agent/agent/` | 模型适配、结构化计划、白名单工具与预算 |
| `src/ai_test_agent/triage/` | 失败分类、证据检查、缺陷草稿与去重 |
| `src/ai_test_agent/evaluation/` | 黄金集执行、指标和基线比较 |
| `tests/`、`fixtures/` | 有针对性的契约/工具/失败治理测试及合成数据 |
| `cases/`、`datasets/` | 审核用例和可共享黄金任务定义 |
| `artifacts/`、`.local/` | 本地原始证据和个人环境配置，禁止加入版本控制 |

建议宿主运行器优先采用 Python，便于文档处理和现有 Android 工具整合；游戏状态桥使用 C#。首版无需 Web 平台、向量数据库或多Agent调度。模型供应商和部署方式由项目的数据权限与预算确定，接口保持可替换。

## 实施中的工作顺序

每个阶段单独生成细化计划，包含实际文件、命令和期望结果。落实以下顺序：

1. 固化可验收的阶段契约和成功/失败例子。
2. 对关键行为先建立失败测试，再实现最小逻辑。
3. 运行自动检查，确认工具错误不会被误分类为业务缺陷。
4. 用真实输入在隔离设备/账号执行，产出本地原始证据。
5. 对照阶段契约审核结果，必要时回滚该阶段变更。
6. 单独提交本阶段实现、文档和脱敏验收报告，再推送用户指定远端。

测试、真实执行、提交、推送各有独立可见进度。没有运行证据不把阶段标记为完成。模型连接失败时完成不依赖它的工具工作，AI能力如实记录为 BLOCKED。

## 决策与资源

- 测试负责人：批准需求口径、用例和黄金标签，判断缺陷有效性。
- 客户端负责人：审核状态桥读取点、测试构建开关和主线程调用，保证发布构建不包含测试端口。
- 后端/运维：提供隔离账号、可审计重置方式、测试服和日志/监控接入。
- Agent/工具实现者：实现宿主工具、运行器、证据和评测，保证错误分类与版本记录。

## 本次需要确认的方案

1. 是否采用“启动冒烟→首次升级状态断言→AI规划”的试点顺序。
2. 是否允许制作专用测试构建并加入只在测试环境生效的Unity状态桥；先在本仓库维护桥代码，游戏接入变更另行审阅。
3. 隔离测试账号、服务器和资源/热更版本如何固定；任何重置是否有明确授权。
4. 一份可用于试点的真实策划需求从哪里取得；缺少时先使用人工验收契约，不能称为JD中的正式需求分析。
5. 模型能否访问项目数据、采用云端还是内网、单次调用成本预算；在确定前不发送项目内容到模型API。

确认设计后可直接实施已确认范围，无需对每个普通开发、测试、提交动作重复确认。
